# Beta: выбор RU-ноги и vibecraft-вход «по ссылке»

> Пояснительная записка к бете: скрытый бета-режим в Android-клиенте, выбор RU-ноги
> (**Стандарт** или **Vibecraft**) и экспериментальный RU-вход, доступный только по
> HTTPS-ссылке. Серверная часть RU-входа живёт в приложении vibecraft (sourcecraft),
> клиентская — в этом репозитории.

## Background

### Для тех, кто видит проект впервые

Chameleon — это VPN с топологией `клиент → RU-вход → зарубежный выход → интернет`.
Клиент (Android/Windows) поднимает туннель до **RU-ноды** (вход на территории РФ),
а та по плечу `ks-relay` передаёт трафик на **зарубежный выход**, откуда он и попадает
в интернет. Транспорт клиента — CITP или KS (оба по UDP), у каждого пользователя свой
порт и свой ключ. Это даёт устойчивость к DPI/ТСПУ и разведению по пользователям.

Весь выбор узлов на клиенте раньше сводился к протоколу (`auto/citp/ks`); сам RU-вход
был один и тот же (`45.90.216.193`), а зарубежный выход выбирался на сервере
автоматически.

### Узкий контекст изменения

Появилась вторая, **экспериментальная** RU-нода — на виртуалке vibecraft. У неё есть
важное ограничение: **нет своего публичного IP, доступна только по HTTPS-ссылке**
(платформенный URL вида `https://p--…-8080.sourcecraft.site`, за Yandex ALB по HTTP/2).
Это значит, что классический UDP-транспорт (KS/CITP) к ней не применим — к vibecraft
нужно ходить **поверх HTTPS**.

> [!NOTE]
> **Почему не WebSocket?** Ссылка отдаётся через ALB по HTTP/2, где апгрейд до WebSocket
> (Extended CONNECT) на практике не проходит. Поэтому транспорт к vibecraft-входу строится
> на обычных HTTP(S)-запросах, а не на WS.

Задача беты: дать тестерам в приложении **выбрать RU-ногу** — привычный «Стандарт» или
новый «Vibecraft (по ссылке)», — не трогая рабочий прод и спрятав всё за скрытой
активацией.

## Intuition

Представьте, что обычный вход — это дверь с известным адресом (IP), в которую стучат по
UDP. Vibecraft-двери адреса нет: к ней ведёт только именованная ссылка, и «постучать»
можно лишь обычным HTTPS-запросом. Поэтому vibecraft работает как **посредник**:

```
телефон ──HTTPS(ссылка)──► vibecraft (RU-вход) ──► зарубежная нога ──► интернет
        ◄───────── ответ возвращается тем же путём ───────────────
```

Конкретный пример проверки: клиент просит `https://ipinfo.io/json`. Если бы запрос шёл
напрямую из РФ, вернулся бы российский адрес. Через vibecraft-ногу ответ показывает
**зарубежный** адрес выхода (например, `20.84.80.164`, США) — доказательство, что трафик
действительно вышел за рубежом.

Активация беты сделана «пасхалкой», чтобы случайный пользователь её не включил:
**8 нажатий по строке версии** в шапке приложения открывают блок выбора ноги.

## Code

### Клиент (этот репозиторий)

**`ProfileStore.kt`** — два новых значения в зашифрованном хранилище: флаг беты и выбор
ноги.

```kotlin
@Synchronized fun betaEnabled():Boolean=read().optBoolean("beta_enabled",false)
@Synchronized fun setBetaEnabled(enabled:Boolean){write(read().put("beta_enabled",enabled))}
@Synchronized fun ruLeg():String=read().optString("ru_leg","standard").let{if(it in setOf("standard","vibecraft")) it else "standard"}
@Synchronized fun setRuLeg(leg:String){require(leg in setOf("standard","vibecraft"));write(read().put("ru_leg",leg))}
```

**`VibecraftLeg.kt`** (новый) — лёгкий клиент управляющего API RU-входа (`/api/ruvpn`).
`probe()` запрашивает список выходов, делает пробный запрос наружу и возвращает реальный
зарубежный адрес выхода:

```kotlin
object VibecraftLeg {
    const val LINK = "https://p--…-8080.sourcecraft.site"
    fun probe(): Probe { /* GET /api/ruvpn/legs → POST /api/ruvpn/fetch → exit.ip */ }
}
```

**`MainActivity.kt`** — скрытая активация и UI:

```kotlin
// строка версии в шапке теперь кликабельна
versionLabel=label("Персональный VPN · v…").apply{isClickable=true;setOnClickListener{onVersionTap()}}

private fun onVersionTap(){
 if(beta)return; betaTaps++
 if(betaTaps>=8){beta=true;store.setBetaEnabled(true);/* показать блок беты */}
 else if(betaTaps>=5){/* «Ещё N до беты…» */}
}
```

`buildBeta()` добавляет на вкладку «VPN» блок с двумя кнопками выбора ноги
(`Стандарт` / `Vibecraft (по ссылке)`) и кнопкой «Проверить Vibecraft-ногу», которая
вызывает `VibecraftLeg.probe()` и показывает зарубежный адрес выхода. Выбор сохраняется
в `ProfileStore` и подсвечивается в `render()`.

> [!IMPORTANT]
> Рабочий прод-путь (UDP KS/CITP до `45.90.216.193`) не менялся. Бета аддитивна:
> выключена по умолчанию, видна только после 8 тапов, выбор «Стандарт» полностью
> повторяет прежнее поведение.

### Сервер (приложение vibecraft, репозиторий sourcecraft)

RU-вход по ссылке — это роуты Next.js:

- `GET /api/ruvpn/legs` — список RU-ног и зарубежных выходов;
- `POST /api/ruvpn/fetch` — релей: принимает URL от клиента, через зарубежную ногу
  (egress-сервис) загружает ресурс и возвращает ответ.

Зарубежная нога — отдельный egress-сервис на выходном узле (`ru-egress.service`,
проверяет bearer-токен; наружу — через nginx `/ru-egress/`). Конфиг ног задаётся
переменной окружения `RU_PROXY_EXITS` (секреты в git не попадают).

## Verification

- `ProfileStore`/`VibecraftLeg`/`MainActivity` собраны без дополнительных зависимостей;
  полная сборка/подпись APK выполняется штатным серверным пайплайном (`gomobile` + Gradle
  + NDK), как и для остальных релизов.
- Сквозной путь **по публичной ссылке** проверен с внешней точки:
  `клиент → ссылка (vibecraft) → US-нога → ipinfo.io` вернул `20.84.80.164` (США) —
  трафик реально вышел за рубежом.
- `GET /api/ruvpn/legs` по ссылке возвращает обе ноги и список выходов.

Ручная проверка на устройстве:
1. Открыть приложение, 8 раз нажать на строку версии в шапке → появляется блок
   «Бета · RU-нога».
2. Выбрать «Vibecraft (по ссылке)», нажать «Проверить Vibecraft-ногу» → в уведомлении
   появляется зарубежный адрес выхода.
3. Переключить на «Стандарт» → поведение подключения прежнее.

## Alternatives

| Подход | Плюсы | Минусы |
|---|---|---|
| **WebSocket-туннель к vibecraft** | Полнодуплексный, ближе к «настоящему» туннелю | Не проходит через ALB/HTTP-2 (Extended CONNECT); ненадёжно |
| **HTTP(S)-релей (выбран)** | Работает через платформенный прокси; просто и проверяемо | Пока прикладной уровень (HTTP), не полный L3-туннель всего трафика |

## Quiz

<details><summary>1. Почему к vibecraft-ноде нельзя подключиться так же, как к стандартной (UDP KS/CITP)?</summary>

- **A. Потому что у vibecraft нет своего IP — доступна только HTTPS-ссылка за ALB.** ✅ Верно: без своего адреса и без прохождения UDP остаётся только транспорт поверх HTTPS.
- B. Потому что KS/CITP устарели. ❌ Они продолжают использоваться на стандартной ноге.
- C. Потому что vibecraft в другой стране. ❌ Vibecraft — RU-вход; дело в способе доступа, а не в стране.
</details>

<details><summary>2. Что именно включают 8 нажатий по строке версии?</summary>

- A. Переключают протокол на KS. ❌ Протокол меняется на вкладке «Протокол».
- **B. Выставляют флаг `beta_enabled` в зашифрованном хранилище и показывают блок выбора RU-ноги.** ✅
- C. Запускают обновление приложения. ❌ Обновления — отдельная вкладка.
</details>

<details><summary>3. Что доказывает успешная «Проверка Vibecraft-ноги»?</summary>

- A. Что телефон подключён к Wi-Fi. ❌ Недостаточно.
- B. Что RU-вход в РФ. ❌ Проверка показывает именно зарубежный адрес.
- **C. Что запрос прошёл через ссылку на vibecraft и вышел наружу с зарубежного адреса выхода.** ✅
</details>

<details><summary>4. Почему выбран HTTP(S)-релей, а не WebSocket?</summary>

- **A. WebSocket-апгрейд не проходит через ALB по HTTP/2.** ✅
- B. WebSocket нельзя использовать в Android. ❌ Можно, дело в платформенном прокси.
- C. HTTP быстрее по определению. ❌ Причина в совместимости, а не в скорости.
</details>

<details><summary>5. Как гарантируется, что бета не ломает рабочий прод?</summary>

- A. Прод-нода отключается на время беты. ❌ Ничего не отключается.
- **B. Бета аддитивна и выключена по умолчанию; выбор «Стандарт» повторяет прежний UDP-путь к `45.90.216.193`.** ✅
- C. Бета заменяет стандартный транспорт. ❌ Наоборот, стандартный путь сохранён без изменений.
</details>
