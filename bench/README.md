# Бенчмарк Chameleon KS

Один скрипт, три независимых бенчмарка, чекпоинты после каждого шага.
Прервали — запустите снова, продолжит с того же места.

```bash
cp bench/bench.env.example bench/bench.env   # или: chameleon-setup (заполнит сам)
make bench-tools                             # bin/ks-stress + bin/ks-hub
scp bin/ks-hub root@<RU-нода>:/opt/chameleon/bench/ks-hub
./bench/bench.sh                             # меню
```

## Что можно запустить

| № | Бенчмарк | Команда | Что меряет | Результат |
|---|---|---|---|---|
| 1 | Сравнение скорости | `bench.sh speed` | Скачивание и RTT: напрямую, через KS, через другие VPN (`SPEED_IF_<имя>`) | `speed.jsonl` |
| 2 | Пользователи и ресурсы | `bench.sh capacity` | Сколько пользователей держит хаб на профилях `vCPU:RAM` из `PROFILES` до выхода за SLA | `capacity.jsonl` |
| 3 | Скорость и число пользователей | `bench.sh scale` | Суммарная и на пользователя скорость, RTT и потери при `SCALE_LEVELS` активных пользователей | `scale.jsonl` |
| — | Всё подряд | `bench.sh all` | 1 → 2 → 3 → отчёт | `REPORT.md` |
| — | Отчёт | `bench.sh report` | Markdown-таблицы по всем собранным данным | `REPORT.md` |
| — | Графики | `bench.sh charts` | SVG: задержка, доля на связи, память, время подключения | `charts/*.svg`, `charts.html` |

Второй аргумент — имя прогона: `bench.sh capacity vps-2cpu`. По умолчанию это дата.

## Чекпоинты

Каждый пункт пишет отметку в `bench/results/<прогон>/state/`. Посмотреть: `bench.sh status`.

- [ ] `prepare` — ключи виртуальных пользователей созданы и скопированы на ноду
- [ ] `speed-<путь>` — замер одного пути (direct, ks, wg…)
- [ ] `cap-<vCPU:RAM>-<N>` — одна ступень нагрузки на одном профиле
- [ ] `cap-<vCPU:RAM>` — профиль закончен, записан максимум пользователей
- [ ] `scale-<N>` — замер при N активных пользователях

Чтобы перемерить шаг, удалите его файл `.done`. Чтобы начать прогон заново: `bench.sh reset <прогон>`.

## Критерий «сервер справляется» (SLA)

Ступень считается пройденной, если одновременно:

- живы ≥ `SLA_ALIVE_PCT` % пользователей (по умолчанию 99 %);
- p95 RTT keepalive ≤ `SLA_P95_MS` (500 мс);
- потери ≤ `SLA_LOSS_PCT` (2 %).

## Безопасность

- Тестовый хаб — отдельный юнит `ks-bench-hub` на отдельном порту (`HUB_PORT`, по умолчанию 51899) со своим TUN `ksb0` и своими ключами. Боевой хаб он не трогает.
- Ресурсы ограничены через systemd (`CPUQuota`, `MemoryMax`, без swap), поэтому профили из п. 2 честно эмулируют маленький VPS.
- Генератор нагрузки (`ks-stress`) работает на отдельной машине. Запуск на самой ноде занижает результат.

## Как читать результаты

- `ka_rtt_ms_p95` — задержка keepalive, главный показатель отзывчивости.
- `alive_users` — сколько клиентов получали ответы в окне измерения.
- `*_loss_pct` < 0 — это не ошибка: ответы на пакеты прогрева пришли уже в окне измерения.
- `mem_peak` — пик памяти тестового хаба в байтах (systemd `MemoryPeak`).
